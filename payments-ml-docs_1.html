01 ── Overview

What Does This Model Do?

Every five minutes, the model reads aggregated signals from across the payments pipeline and answers one question: Is an incident about to occur — and if so, what kind?

The payment pipeline processes thousands of transactions per minute across FedNow, TCH RTP, ACH, and Wire rails. When something goes wrong — a rule regression, a connector failure, a GL lock — the impact cascades quickly. By the time a human operator notices an error spike, dozens of transactions may already be in the dead letter queue, and premium clients may already be breaching their SLA.

This model moves the detection window earlier. Rather than reacting to errors after they appear in dashboards, it monitors the subtle precursors — rising queue depths, latency inflections, deployment timestamps, connector connection counts — and predicts the incident type with enough lead time to prevent client impact.

"We don't want to know what broke. We want to know what is about to break — and why."

Every prediction comes with a SHAP-based explanation: a ranked list of the specific signals that drove the alert, expressed in plain language that an operations team member or relationship manager can act on immediately.

02 ── Model Architecture

Why Gradient Boosted
Decision Trees?

The choice of algorithm matters enormously. We evaluated four model families against this specific problem before selecting XGBoost gradient-boosted trees as the production architecture.

⚡
The Core Insight: Payment telemetry is structured tabular data with non-linear interactions between features (e.g., a high thread pool utilisation is only dangerous combined with a recent deployment). Gradient-boosted trees capture these interactions natively, without requiring feature engineering to express them explicitly. Academic research from 2022 confirms tree-based models outperform deep learning on structured tabular datasets of this type by 5–15% F1 on average.

How Gradient Boosting Works

🌳
Sequential Tree Building
The boosting mechanism

XGBoost builds 400 decision trees sequentially. Each new tree focuses on correcting the mistakes made by the previous trees — this is the "boosting" concept. The result is a highly accurate ensemble where each tree contributes a small, specialised correction.

Unlike a random forest (which builds trees independently), boosting ensures that rare patterns — like the specific combination of signals that precede a Financial Exposure incident — are not lost in averaging.

⚖️
Severity-Weighted Training
Not all mistakes are equal

A missed Financial Exposure alert is far more costly than a false alarm. We train the model with severity-scaled sample weights that explicitly encode this business logic:

IncidentSeverity ×Rationale
No Incident1.0×Baseline
Rule Regression2.5×Wide client impact
Connector Failure2.0×Rail availability risk
GL Lock1.8×Predictable but impactful
Financial Exposure3.5×Inter-bank obligation risk

Probability Calibration

Raw XGBoost probabilities can be overconfident — the model may output 0.97 confidence when its true accuracy at that level is 0.88. Overconfident scores would make it impossible to set reliable alerting thresholds. We apply Platt scaling (a logistic regression layer fitted on held-out validation data) to produce calibrated probabilities. After calibration, when the model says 85% confidence, it is correct approximately 85% of the time.

04 ── Explainability

SHAP: Every Alert Explained

An alert without an explanation is noise. Every single prediction from this model is accompanied by a SHAP explanation — a ranked list of the signals that drove it, expressed in terms an operator can immediately act on.

📐
What is SHAP? SHAP (SHapley Additive exPlanations) is a mathematical framework rooted in cooperative game theory. It assigns each feature a contribution score φᵢ such that the sum of all contributions equals the difference between the prediction and the average prediction. This additive property gives it a crucial guarantee: the explanation is complete and consistent — no feature's contribution can be hidden or double-counted.

How to Read a SHAP Explanation

For each prediction, the model produces a waterfall of contributions. Features shown in teal push the prediction toward the incident class. Features in rose reduce the risk score. The magnitude of the bar shows how much each feature contributed.

💬
Example operator message: "Predicted RULE_REGRESSION at 91% confidence. Primary driver: error_rate_spike_ratio = 47.2 (89× normal), combined with rule_version_changed = 1 (RTP-RULES-v2.3 deployed 4 minutes ago). Recommend immediate rollback review."

05 ── False Positive Reduction

Three Layers of FP Reduction

Alert fatigue is as dangerous as no alerting at all. Operators who receive too many false alarms stop trusting the system. We apply three independent filters before any alert fires.

⚠
The False Positive Problem: A model trained to maximise accuracy on imbalanced data (94% no-incident windows) will learn to always predict "no incident" and achieve 94% accuracy — while being completely useless. Our three-layer strategy ensures precision and recall are independently optimised for each severity tier.
1
Threshold Shift — 0.50 → 0.65
The default decision boundary of 0.50 maximises F1 but produces too many low-confidence alerts. We shift to 0.65, requiring the model to be substantially confident before firing. This reduces false positives by approximately 30% while retaining 96%+ recall on CRITICAL incidents (Rule Regression, Financial Exposure). The threshold was selected by sweeping the precision-recall curve on held-out validation data, optimising for the point where FP rate drops below 4%.
config: threshold=0.65 · impact: ~30% FP reduction
2
Burst Confirmation — 2 of 3 Consecutive Windows
A single anomalous 5-minute window is often a transient spike — a brief GC pause, a network hiccup, a momentary queue backup — that self-corrects within minutes. We suppress single-window alerts and only fire when the same incident class is predicted in at least 2 of the last 3 consecutive windows (10–15 minutes of sustained signal). This eliminates approximately 35% of false positives caused by transient load without materially delaying detection of genuine incidents.
config: min_consecutive=2 of 3 · impact: ~35% FP reduction
3
Confidence Floor — ADVISORY Below 0.72
Predictions with calibrated probability between 0.65 and 0.72 are real predictions — the model genuinely thinks something is wrong — but its confidence is not high enough to wake someone up. These are published as ADVISORY status to the Observatory dashboard, visible to monitoring teams, but do not trigger PagerDuty alerts or agent actions. Only predictions at ≥0.72 confidence escalate to full ALERT status. This reduces overnight wake-ups by approximately 20% with no loss of CRITICAL incident recall.
config: confidence_floor=0.72 · impact: ~20% alert reduction

Section 1 — Synthetic Data Generation

In production, the feature store is populated from the pay.events.normalised Kafka stream via a Flink SQL job that computes 5-minute tumbling window aggregations. For training, we generate statistically realistic synthetic data that mirrors the real distribution of each incident type.

incident_predictor.py · Section 1 — Data Generation (excerpt) Python 
# Class sizes mirror real-world incident frequency.
# Incidents are rare — 94% of windows are healthy.
# We use stratified oversampling so the model learns
# from enough incident examples to generalise.
CLASS_SIZES = {
    0: 6000,   # NO_INCIDENT        — majority class
    1: 1000,   # RULE_REGRESSION    — ~1–2/week in active deployments
    2:  800,   # CONNECTOR_FAILURE  — correlated with high load
    3:  600,   # GL_PERIOD_LOCK     — monthly, predictable
    4:  400,   # FINANCIAL_EXPOSURE — rarest, highest severity
}

def generate_window(incident_type: int, window_idx: int) -> dict:
    """
    Generate one 5-minute telemetry window with features that are
    statistically consistent with the given incident type.
    Each incident type has distinctive signal patterns:
      - Rule Regression:   DATA error spike + recent deployment timestamp
      - Connector Failure: SYSTEM errors + thread pool ≥85% + ACK timeouts
      - GL Lock:           Near-zero settlement + month-end temporal features
      - Financial Exposure: exposure_gap ≫ 0 + gl_posted_count ≈ 0
    """
    # Seeded RNG per window for reproducibility
    rng = np.random.RandomState(window_idx * 7 + incident_type * 13)

    if incident_type == 1:  # RULE_REGRESSION
        spike = rng.uniform(15, 60)          # 15×–60× baseline error rate
        f["error_rate_spike_ratio"] = spike
        f["data_error_count"]      = rng.randint(25, 120)   # DATA errors dominate
        f["rule_version_changed"]  = 1                     # KEY: recent deploy
        f["deployment_error_corr"] = rng.uniform(0.60, 0.95) # Strong correlation
        f["validation_p95_ms"]    *= rng.uniform(2.0, 5.5) # Validation latency up
        f["icon_queue_depth"]     = rng.randint(800, 4000)  # Queue backing up
    
    elif incident_type == 4:  # FINANCIAL_EXPOSURE
        f["positive_ack_sent_count"] = rng.randint(8, 40)
        f["gl_posted_count"]        = rng.randint(0, 3)  # KEY: near zero
        f["exposure_gap"]           = (
            f["positive_ack_sent_count"] - f["gl_posted_count"]
        )  # This is the defining financial risk signal

Section 2 — Class Weights & Severity Scaling

Standard class weighting balances the frequency imbalance between 6,000 healthy windows and 400 financial exposure windows. Severity scaling multiplies these weights further — telling the model that missing a Financial Exposure incident is 3.5× more costly than missing a No-Incident classification.

incident_predictor.py · Section 2 — Severity-Weighted Training Python 
# Severity multipliers encode business risk logic into the training loss.
# The model will penalise missing a Financial Exposure incident
# 3.5× more than it penalises a false alarm on that class.
severity_scale = {
    0: 1.0,   # No Incident    — baseline
    1: 2.5,   # Rule Regression — wide client impact
    2: 2.0,   # Connector Failure
    3: 1.8,   # GL Period Lock
    4: 3.5,   # Financial Exposure — highest business risk
}

# Frequency-inverse weight × severity multiplier per training sample
sample_weights = np.array([
    (n_total / (n_classes * class_counts[yi])) * severity_scale[yi]
    for yi in y_train
])

# Pass sample_weights to XGBoost's fit() — this reshapes the loss function
# without changing the prediction output format
model.fit(
    X_train, y_train,
    sample_weight=sample_weights,
    eval_set=[(X_val, y_val)],
)

# TreeSHAP: exact SHAP values for tree ensembles in polynomial O(TLD) time.
# Returns one (n_samples × n_features) matrix per class.
explainer  = shap.TreeExplainer(model_base)
shap_values = explainer.shap_values(X_test)  # shape: [5, n_test, n_features]

# ── Production inference function ─────────────────────────────────────────
def predict_incident(
    window_features: dict,
    threshold: float = 0.65,         # Tuned for FP reduction
    confidence_floor: float = 0.72,   # Below this → ADVISORY, not ALERT
) -> dict:
    row   = pd.DataFrame([window_features], columns=FEATURE_COLUMNS)
    proba = model_calibrated.predict_proba(row)[0]
    pred_class  = int(np.argmax(proba))
    confidence  = float(proba[pred_class])

    # Three-tier alert level
    if   pred_class == 0 or proba[pred_class] < threshold:
        alert_level = "NONE"
    elif confidence < confidence_floor:
        alert_level = "ADVISORY"     # Dashboard only, no page
    else:
        alert_level = "ALERT"        # Fires PagerDuty + agent

    # SHAP explanation for the predicted class
    shap_vals   = explainer.shap_values(row)[pred_class][0]
    top_features = sorted(
        zip(FEATURE_COLUMNS, row.iloc[0].values, shap_vals),
        key=lambda x: abs(x[2]), reverse=True
    )[:5]

    # Human-readable one-liner — consumed by AI agents (John / Michel / Aria)
    top_feat, top_val, top_sv = top_features[0]
    top_explanation = (
        f"Predicted {INCIDENT_TYPES[pred_class]} ({confidence:.0%} confidence). "
        f"Primary driver: {top_feat.replace('_', ' ')} is elevated "
        f"(value={top_val:.2f}, SHAP={top_sv:+.3f})."
    )

    return {
        "incident_type":   INCIDENT_TYPES[pred_class],
        "alert_level":     alert_level,       # "NONE" | "ADVISORY" | "ALERT"
        "confidence":      confidence,
        "probabilities":   {INCIDENT_TYPES[i]: proba[i] for i in range(5)},
        "explanation":     [...],              # Top 5 SHAP features
        "top_explanation": top_explanation,    # Plain-language one-liner
    }

Why 5-fold cross-validation? Training on 60% of data and evaluating on a fixed 20% test set can produce lucky or unlucky splits. 5-fold CV rotates through five different train/test splits and averages the results, giving a much more reliable estimate of real-world performance. The tight standard deviation (±0.008) confirms the model generalises consistently rather than overfitting to specific windows.

Retraining Policy

📅
Scheduled Retraining
Weekly cadence

The model is retrained weekly on a rolling 90-day window of production telemetry. This ensures it adapts to seasonal patterns (e.g., quarter-end GL lock windows), new rule engine versions, and changes in payment volume distribution.

📡
Drift Detection
Triggered retraining

A separate drift monitor computes the Population Stability Index (PSI) on the 10 most important features daily. When PSI > 0.15 for any key feature (indicating the production distribution has shifted materially from training data), an out-of-cycle retraining is triggered automatically.

08 ── Deployment

From Model to Production Alert

The trained model is served as a microservice within the Observatory platform. It consumes from the pay.events.normalised Kafka stream and publishes predictions to pay.alerts.sre.

1
Feature Aggregation (Flink SQL)
A Flink SQL job reads pay.events.normalised and computes 5-minute tumbling window aggregations, producing the 41-feature vector in real-time.
Latency: <30s · SLA: 99.9% window completeness
2
Model Inference (FastAPI microservice)
The feature vector is POSTed to the prediction service. The calibrated XGBoost model returns the prediction + SHAP explanation in <50ms. The service runs 3 replicas with a warm model in memory.
Endpoint: POST /v1/predict · SLA: p99 <50ms
3
Burst Confirmation Buffer (Redis)
Predictions are written to a Redis time-series. The burst confirmation logic reads the last 3 windows and fires only if ≥2 predict the same incident class.
TTL: 20 minutes · check on each new prediction
4
Alert Publication (Kafka + PagerDuty)
Confirmed alerts are published to pay.alerts.sre and simultaneously trigger the AI agent (John/Michel/Aria) with the full SHAP explanation. ADVISORY predictions are published to the dashboard only.
pay.alerts.sre · pay.agent.actions
5
Human Review & Feedback Loop
Operators who receive an alert can mark it as correct, false positive, or missed incident. This feedback is logged to the training data store and used in the next weekly retraining cycle, continuously improving the model.
Feedback → training store → weekly retrain
🔒
Model Governance

Every model version is stored with a full metadata record: training date, data window, hyperparameters, performance metrics, and the operator who approved the promotion to production.

Model promotions require a pull request with performance comparison against the current production model. A regression in recall on Financial Exposure class blocks promotion automatically.

Shadow mode: New model versions run alongside the production model for 48 hours before promotion, with predictions logged but not actioned, to validate real-world performance.

🛡
Human Override Always Wins. The model predicts and explains. The AI agents translate predictions into recommendations. Humans approve or reject actions. No automated remediation occurs based on model output alone — this is a hard architectural constraint, not a policy choice.

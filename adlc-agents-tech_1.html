Conceptual Overview
What is an Agent?
An ADLC agent is not a script or a workflow. It is an autonomous software process that combines a large language model's reasoning with structured tools, persistent memory, and a messaging interface — enabling it to solve open-ended domain problems without step-by-step human instruction.
🤖
The one-sentence definition
Agent = LLM brain + Python tools + Redis memory + Kafka I/O

Think of each agent as a specialist contractor. The LLM (Claude) provides the reasoning, judgement, and language skills. Python functions (called "tools") give it hands — the ability to actually query databases, run tests, generate code files, and call APIs. Redis gives it a notepad to remember what it's doing mid-task. Kafka is the internal post room: it receives work from upstream agents and dispatches its completed artefacts downstream.

Critically, no agent is hard-coded with IF/THEN logic for its domain. The REQ-AGENT does not contain a list of question templates. The QE-AGENT does not contain a fixed test catalogue. Instead, each agent is given a system prompt that defines its role, access to domain-specific tools, and the current task context — and it figures out what to do from there. This is what makes it agentic rather than scripted.

The think → act → observe loop

Every ADLC agent operates on the same fundamental loop — often called the ReAct pattern (Reasoning + Acting). This loop repeats until the agent determines it has produced a complete, valid artefact and emits it to the message bus.

1
Think — LLM reasons about the task
Claude receives the system prompt (defining the agent's role and constraints), the task context (project ID, upstream artefacts), and any tool results from previous iterations. It reasons about what needs to happen next and decides whether to call a tool or produce final output.
claude-sonnet-4-6 · messages API · ~800ms per reasoning step
2
Act — Python executes the chosen tool
If Claude's response contains a tool_use block, the Python runtime calls the corresponding function with Claude's chosen parameters. Tools are real functions — they run SQL queries, call APIs, read files, execute test suites, or generate code. They are not simulated.
Python 3.11 · asyncio · actual I/O operations
3
Observe — tool result fed back to Claude
The tool's return value is appended to the conversation as a tool_result message. Claude can now see the outcome of its action — e.g. the actual row count and null percentage from a profiling query — and decides what to do next. This creates a genuine feedback loop rather than a single-shot response.
tool_result role · structured JSON · typed Pydantic models
4
Emit — artefact published to Kafka
When Claude determines the task is complete, it produces a structured JSON artefact (validated against a Pydantic schema). The Python runtime serialises this with Avro and publishes it to the appropriate Kafka topic. The orchestrator picks it up, updates gate state, and triggers the downstream agent if a gate has been approved.
confluent-kafka-python · Avro serialisation · Schema Registry

The BaseAgent class

All eight ADLC agents inherit from a single BaseAgent class. This base class wires the four components together and implements the think → act → observe loop. Each specific agent only needs to define: its system prompt, its tool set, and its output artefact schema. Nothing else is agent-specific at the infrastructure level.

ℹ
Why inheritance over composition here? Because all agents share an identical execution model. Composition would have been appropriate if agents had meaningfully different loop structures — but they don't. The only variation is in prompts and tools.

Domain knowledge lives in prompts

The REQ-AGENT's ability to elicit requirements is not encoded in Python. It is encoded in a carefully crafted system prompt that defines the agent's persona, methodology, output format, and escalation rules. The Python code is identical infrastructure for all agents.

💡
Key insight: Adding a ninth agent to the ADLC requires writing a new system prompt, a new set of tools, and a new Pydantic artefact schema — not new infrastructure code. The runtime is fully reusable.

Tech Stack — Layer 1
The LLM Layer
Claude Sonnet 4.6 is the reasoning engine inside every agent. It receives a rich context — the system prompt, conversation history, tool results — and decides what to do next. It never writes to a database or calls an API directly; those actions belong to the tool layer.

System prompts define agent identity

Each agent has a unique system prompt that acts as its complete operating manual. The prompt specifies the agent's role, the methodology it must follow, the exact format of its output artefact, the conditions under which it must escalate to a human rather than guessing, and the quality bar its output must clear before emitting. The system prompt is version-controlled alongside the code and reviewed at every gate.

The Messages API call structure

Every iteration of the think→act loop makes a single call to anthropic.messages.create(). The conversation history grows with each iteration as tool results are appended. Claude sees the full history of what it has already tried and what the results were, enabling it to course-correct and make informed decisions about subsequent tool calls.

base_agent.py · Core LLM call inside the execution loop Python 
import anthropic
from typing import AsyncIterator

class BaseAgent:
    def __init__(self, config: AgentConfig):
        self.client = anthropic.AsyncAnthropic()
        self.config = config          # holds system_prompt, tools, artefact_schema
        self.redis  = RedisStore()
        self.kafka  = KafkaBus()

    async def _think(
        self,
        messages: list[dict],
        tools: list[dict]
    ) -> anthropic.types.Message:
        """One reasoning step — Claude decides: call a tool, or emit final output."""
        return await self.client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            system=self.config.system_prompt,
            tools=tools,
            messages=messages,
        )

    async def run(self, task: Task) -> Artefact:
        """Main execution loop: think → act → observe → repeat."""
        ctx      = await self.redis.load_context(task.project_id)
        messages = build_initial_messages(task, ctx)
        tools    = self.config.get_tool_schemas()

        while True:
            response = await self._think(messages, tools)

            # Claude chose to call one or more tools
            if response.stop_reason == "tool_use":
                tool_results = await self._execute_tools(response.content)
                messages = append_tool_results(messages, response.content, tool_results)
                continue

            # Claude produced final text output — parse it as an artefact
            if response.stop_reason == "end_turn":
                artefact = self.config.artefact_schema.parse_llm_output(response)
                await self.kafka.emit_artefact(task.handoff_topic, artefact)
                return artefact
⚡
Why claude-sonnet-4-6 specifically? Three reasons: (1) its tool use reliability is significantly higher than smaller models, reducing loop iterations; (2) its 200k context window lets the DE-AGENT hold the entire data model, all business rules, and the pipeline code it's generating in a single context; (3) its JSON output consistency is high enough that Pydantic validation rarely requires retries.
Tech Stack — Layer 2
Tool Use — Agent Hands
Tools are ordinary Python functions decorated with a Pydantic schema that describes their signature to Claude. When Claude calls a tool, the Python runtime executes the actual function and returns the result. This is how agents interact with the real world — databases, file systems, APIs, test runners.

How tool use works

The Anthropic Messages API accepts a tools parameter — a list of JSON schemas describing each available function. Claude reads these schemas and, when it decides an action is needed, returns a tool_use content block specifying which function to call and with what arguments. The Python runtime matches this to the actual function and executes it. The result is sent back as a tool_result message.

from pydantic import BaseModel, Field
from adlc.tools import tool, ToolResult
import sqlalchemy as sa
import pandas as pd

# --- Input schema (what Claude must provide) ---
class ProfileTableInput(BaseModel):
    source_system: str = Field(..., description="Source system ID from the data domain map")
    table_name:    str = Field(..., description="Fully-qualified table name to profile")
    sample_rows:   int = Field(1_000_000, description="Row sample size for profiling")
    columns:       list[str] | None = Field(None, description="Specific columns, or None for all")

# --- Output schema (what Python returns to Claude) ---
class ProfileTableResult(BaseModel):
    row_count:        int
    column_profiles:  list[ColumnProfile]  # completeness, cardinality, min/max, nulls
    detected_pk:      str | None             # inferred primary key candidate
    quality_warnings: list[str]              # e.g. "amount col has 2.1% nulls"

# --- The @tool decorator registers this with the agent's tool registry ---
@tool(
    name="profile_table",
    description="Run a statistical data quality profile on a source table. "
                "Returns completeness, uniqueness, cardinality, and anomaly warnings."
)
async def profile_table(inp: ProfileTableInput) -> ProfileTableResult:
    engine = get_source_engine(inp.source_system)  # read-only credentials from Secrets Manager
    async with engine.connect() as conn:
        df = await conn.run_sync(
            lambda c: pd.read_sql(
                f"SELECT * FROM {inp.table_name} TABLESAMPLE SYSTEM(10) LIMIT {inp.sample_rows}",
                c
            )
        )
    profiles  = [build_column_profile(df, col) for col in df.columns]
    pk        = infer_primary_key(df)
    warnings  = [p.warning for p in profiles if p.warning]
    return ProfileTableResult(
        row_count=len(df), column_profiles=profiles,
        detected_pk=pk, quality_warnings=warnings
    )

Tool registries per agent

Each agent has a ToolRegistry — the set of tools it is permitted to use. The registry determines what Claude can do within that agent's scope. This is by design: the REQ-AGENT cannot accidentally call a database directly because it does not have database tools. The only agent that can run code is the DE-AGENT. The only agent that can deploy infrastructure is the DEP-AGENT.

Tech Stack — Layer 3
Memory & State
Agents are stateless microservices — they hold no in-process state between requests. All memory is externalised across three stores, each serving a different time horizon: Redis for hot in-flight context, PostgreSQL for permanent audit records, and S3 for artefact content.
⬡ Hot store
Redis
Conversation history, phase status, artefact URIs. 24h TTL.
⬡ Cold store
PostgreSQL
Gate approvals, agent runs, artefact hashes. Immutable append-only.
⬡ Artefact store
S3
All phase outputs: FSD, contracts, code, reports. Versioned buckets.

Redis: conversation history for multi-step tasks

A single agent phase often requires multiple LLM iterations — the DA-AGENT might make 8–12 tool calls across three source tables before it has enough data to build a complete logical model. Redis stores the growing messages list between iterations, so each _think() call receives full context of every action taken so far. This is what enables genuine reasoning-across-steps rather than each call starting fresh.

state/redis_store.py · Loading and persisting agent context Python 
from redis.asyncio import Redis
from adlc.models import AgentContext

class RedisStore:
    def __init__(self):
        self.r = Redis.from_url(settings.REDIS_URL, decode_responses=True)
        self.TTL = 86_400  # 24 hours

    async def load_context(self, project_id: str) -> AgentContext:
        raw = await self.r.get(f"ctx:{project_id}")
        if not raw:
            return AgentContext(project_id=project_id, messages=[], artefacts={})
        return AgentContext.model_validate_json(raw)

    async def save_context(self, ctx: AgentContext) -> None:
        # Serialise full context including growing messages list
        await self.r.setex(
            name=f"ctx:{ctx.project_id}",
            time=self.TTL,
            value=ctx.model_dump_json()
        )

    async def append_tool_result(
        self, project_id: str,
        tool_call: dict, tool_result: dict
    ) -> None:
        # Atomic append to messages list — avoids race conditions
        ctx = await self.load_context(project_id)
        ctx.messages.append({"role": "assistant", "content": [tool_call]})
        ctx.messages.append({"role": "user",      "content": [tool_result]})
        await self.save_context(ctx)

PostgreSQL: the immutable audit log

Every gate approval, every agent execution, and every artefact hash is written to PostgreSQL as an immutable append-only record. This is not just good practice — the target platform's PCI-DSS compliance requires a complete, tamper-evident audit trail of all data management decisions. The schema uses INSERT only; there are no UPDATE or DELETE operations on audit tables.

db/models.py · PostgreSQL schema (SQLAlchemy 2 declarative) Python 
from sqlalchemy.orm import DeclarativeBase, mapped_column, Mapped

Tech Stack — Layer 4
The Kafka Message Bus
Agent handoffs are not HTTP calls. They are events on a Kafka message bus — typed with Avro schemas, validated by the Schema Registry, and consumed by the downstream agent when it is ready. This decoupling is what makes the ADLC resilient and observable.
🔁
Why Kafka over direct HTTP? If the WIRE-AGENT is restarting when REQ-AGENT finishes, a direct HTTP call fails and the work is lost. With Kafka, the event sits in the topic until WIRE-AGENT is healthy and consumes it. The ADLC never loses a completed phase's work due to a transient failure in the next agent.

Topic structure

Each of the 14 handoff events in the lifecycle maps to a dedicated Kafka topic. Topic names follow the pattern adlc.handoff.{from}-to-{to}. Feedback loop topics (QE routing failures back to DE) use adlc.feedback.{from}-to-{to}.

Three Agents Walked Through
The following walkthroughs show the full implementation of three representative agents — REQ-AGENT (discovery), DE-AGENT (builder), and QE-AGENT (gatekeeper) — from system prompt through tool execution to artefact emission.

REQ-AGENT — Requirements Gathering

The simplest agent in terms of tool footprint, but the most consequential: a poor FSD cascades failures through every downstream phase. REQ-AGENT's tools are deliberately narrow — it cannot query databases or write code. Its only instruments are: reading project context, requesting stakeholder input, and detecting requirement conflicts.

DE-AGENT — Data Engineering

The most technically complex agent. It receives sealed data contracts and a logical data model and must generate production-grade dbt SQL, ingestion connectors, and OpenAPI specs — all in a single phase. It uses a generate_dbt_model tool that renders Jinja2 templates seeded with data contract fields, then runs the model through a schema validator before writing to Git.

async def generate_dbt_model(inp: GenerateDbtModelInput) -> GenerateDbtModelResult:
    contract = await load_contract(inp.contract_id)   # reads from S3
    jinja    = Environment(FileSystemLoader("de_agent/templates"))

    # Render the SQL template — injects contract fields, SLA config, BR hooks
    sql = jinja.get_template("incremental_model.sql.j2").render(
        contract        = contract,
        mandatory_fields= contract.get_mandatory_fields(),
        freshness_sla   = contract.sla.freshness_max_min,
        unique_key      = contract.get_primary_key(),
    )
    # Render schema.yml with column tests derived from quality thresholds
    schema = jinja.get_template("schema.yml.j2").render(
        contract = contract,
        tests    = build_column_tests(contract)
    )
    # Validate: dbt parse must succeed before we commit
    parse_result = await dbt_parser.parse_model(sql, schema)
    if not parse_result.valid:
        raise ToolError(f"dbt parse failed: {parse_result.errors}")

    commit_sha = await commit_to_git(contract.id, sql, schema)
    return GenerateDbtModelResult(
        model_name=contract.asset_name, sql_content=sql, schema_yaml=schema,
        test_count=len(build_column_tests(contract)),
        schema_valid=True, git_commit_sha=commit_sha
    )

QE-AGENT — Quality Engineering

The gatekeeper. QE-AGENT has two critical responsibilities: proving that all 31 acceptance criteria are met, and blocking the lifecycle if they are not. Its route_failures tool is what enables targeted remediation — rather than declaring the entire build phase failed, it produces a structured FailureRoutingPackage that tells the DE-AGENT exactly which model, which rule, and which column needs fixing.

from great_expectations import get_context
from great_expectations.core import ExpectationSuite
from adlc.tools import tool

class MeasureDQInput(BaseModel):
    contract_id:  str
    environment:  str = "staging"
    sample_rows:  int = 10_000_000

class DQScorecard(BaseModel):
    completeness: float    # % non-null on mandatory fields
    accuracy:     float    # % records passing all BR evaluations
    consistency:  float    # % cross-system reconciliation match rate
    timeliness:   float    # % records within freshness SLA
    uniqueness:   float    # % unique on primary key columns
    overall_pass: bool     # True only if ALL dimensions >= threshold
    failures:     list[DQFailure]

@tool(name="measure_dq_dimensions",
      description="Measure all 5 DQ dimensions against a sealed data contract. "
                  "Returns per-dimension scores and a pass/fail for G5 gate eligibility.")
async def measure_dq_dimensions(inp: MeasureDQInput) -> DQScorecard:
    contract = await load_contract(inp.contract_id)
    ctx      = get_context()  # great_expectations context

    # Build GE expectation suite from contract quality_rules
    suite = ExpectationSuite(expectation_suite_name=contract.id)
    for rule in contract.quality_rules:
        suite.add_expectation(rule_to_expectation(rule))

    # Run validations against staging DB — real SQL executed by GE
    results = ctx.run_validation_operator(
        "action_list_operator",
        assets_to_validate=[get_staging_batch(contract, inp.sample_rows)],
        run_id=f"qe-{contract.id}-{datetime.utcnow().isoformat()}"
    )

    # Compute dimension scores from GE results
    completeness = score_completeness(results, contract.mandatory_fields)
    accuracy     = score_accuracy(results,     contract.quality_rules)
    consistency  = score_consistency(results,   contract.id)
    timeliness   = score_timeliness(results,    contract.sla.freshness_max_min)
    uniqueness   = score_uniqueness(results,    contract.primary_key)

    thresholds = contract.quality_thresholds
    overall    = (
        completeness >= thresholds.completeness and
        accuracy     >= thresholds.accuracy     and
        consistency  >= thresholds.consistency  and
        timeliness   >= thresholds.timeliness   and
        uniqueness   >= thresholds.uniqueness
    )
    return DQScorecard(
        completeness=completeness, accuracy=accuracy,
        consistency=consistency,  timeliness=timeliness,
        uniqueness=uniqueness,     overall_pass=overall,
        failures=collect_failures(results)
    )
Engineering Principles
Patterns & Principles
Seven engineering principles govern how every ADLC agent is written. These are not guidelines — they are enforced at code review and checked by static analysis in the CI pipeline.
P1
No domain logic in Python — it lives in prompts
Python code in agents must be infrastructure-only: wiring, I/O, validation, serialisation. If you find yourself writing an IF statement that encodes a business rule — "if requirement has no owner, flag it" — that logic belongs in the system prompt, not the code. This keeps agents flexible: behaviour changes are a prompt update, not a deployment.
Enforced by: code review checklist · pylint custom rule
P2
Every tool input and output is a Pydantic model
No dict or Any at tool boundaries. Every tool's input and output is a typed Pydantic model with field-level documentation. This serves two purposes: Claude gets accurate schema documentation (it reads the field descriptions when deciding what to pass), and the Python runtime gets automatic validation — malformed tool calls fail fast with a clear error rather than silently producing garbage.
Enforced by: mypy strict · pydantic-validator CI check
P3
Agents are stateless — all state is externalised
An agent process must be killable and restartable at any point without data loss. No in-memory state that cannot be reconstructed from Redis, PostgreSQL, or S3. This enables zero-downtime deployments, horizontal scaling (multiple pods for the same agent), and clean crash recovery — the agent just reloads its context from Redis and resumes where it left off.
Enforced by: k8s liveness probe · chaos testing in staging
P4
Escalate rather than hallucinate
Every agent's system prompt explicitly defines the conditions under which it must call escalate_to_human() and halt. An agent must never resolve ambiguity by guessing. Uncertainty in the LLM's reasoning is a feature — if Claude is not confident about a requirement conflict or a schema interpretation, the correct action is to surface that uncertainty to a human, not to pick the most plausible answer and continue.
Enforced by: prompt review · escalation rate monitoring (target: under 8%)
P5
Tool calls are idempotent
Every tool must be safe to call multiple times with the same arguments. If the DA-AGENT's pod restarts mid-phase and it re-calls profile_table() on a table it already profiled, it must return the same result and not create duplicate records. This is enforced by content-addressable artefact storage (SHA-256 keyed) and upsert-not-insert semantics in all write operations.
Enforced by: idempotency unit tests · idempotency-key header on all S3 writes
P6
Artefact schemas are versioned and backward-compatible
Every Pydantic artefact model and Avro schema in the Confluent Schema Registry follows semantic versioning. A change that adds a new optional field is a minor version bump and is backward-compatible. A change that removes a field or changes a type is a major version bump, requires a new topic, and cannot be deployed without a coordinated rollout of both producer and consumer agents. The Schema Registry enforces compatibility rules automatically.
Enforced by: Schema Registry compatibility check · pre-commit schema lint
P7
Every agent is independently testable
Each agent ships with a mock client that replaces the real Anthropic API with a deterministic stub for unit testing. Tool functions are tested with real external calls against a local Docker Compose stack (PostgreSQL, Redis, Kafka, stub S3). Integration tests run against a full staging environment. No agent's test suite depends on another agent being deployed — isolation is a first-class constraint.
Enforced by: CI pipeline gate · coverage threshold: 80% per agent
🎯
The meta-principle behind all seven: The ADLC agents are designed to be boring infrastructure for remarkable capability. The interesting work — domain expertise, reasoning, judgement — belongs to Claude. The Python code exists only to give Claude reliable, safe, typed tools to act on that reasoning in the real world. Keep the two concerns cleanly separated and the system stays maintainable as both the LLM and the domain evolve.
